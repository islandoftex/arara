Every great journey starts with a single step. Mine started on a rainy
weekend, which sounds like the opening of a novel but is, in fact,
exactly what happened. I was looking at our projects, trying to find
opportunities for improvements, when I had a spark. I should pay a
visit to our beloved bird, the project that started the entire Island
of TeX. And just like that, I decided to take arara under my
wings and help it soar.

<!-- more -->

The last major release was back in 2022, and earlier this year we
told you, quite honestly, that the ideas floating around for a v8 had
no real demand. Both things were true at the time. What changed was
not the demand. What changed was me, on that rainy weekend,
remembering that demand is not the only reason to build something.
Some projects you build because people need them. Others you build
because you love them. arara has always been a bit of both.

Let me tell you how we got here. It is a long story, and it involves
nine libraries, one bird, a million dollar mistake, and two friends
who somehow never stopped caring about a TeX automation tool.

## The library explosion

Here is something I did not expect: every single idea we had to
improve arara refused to stay inside arara. Each one grew legs,
walked out the door, and became its own project. I am not
exaggerating. Let me count them for you.

The manual needed to be written in Markdown and converted into
properly typesettable TeX, so we wrote
[CoralMark](https://gitlab.com/islandoftex/libraries/coralmark), a
library that converts Markdown into whatever format you need (and
can also extract and process blocks along the way). The diagrams in
the manual needed to be rendered through a remote service, so we
built [CrocPlot](https://gitlab.com/islandoftex/libraries/crocplot)
to speak to diagram renderers. The rendered figures needed to become
proper vector PDFs, so
[SVGecko](https://gitlab.com/islandoftex/libraries/svgecko) was born,
a small library that takes an SVG and gives you back a vector PDF, no
rasterization involved. Our end-to-end smoke suite needed a runner
for its scenarios, so we wrote
[Kobats](https://gitlab.com/islandoftex/libraries/kobats). The
copyright headers in every source file needed updating year after
year, so
[ChronoHeader](https://gitlab.com/islandoftex/libraries/chronoheader)
took over that chore. The version number needed to come from the
changelog instead of from someone remembering to bump a string, so
[Solstice](https://gitlab.com/islandoftex/libraries/solstice)
learned to read it. The packaging for CTAN needed to stop being a
pile of hand-rolled Gradle tasks, so
[LeoPack](https://gitlab.com/islandoftex/libraries/leopack) was
born. The man page needed writing without typing raw roff, so
[ScribeSwan](https://gitlab.com/islandoftex/libraries/scribeswan)
gave us a proper builder. And when the new website needed the TeX
logo treated with the respect it deserves (lowered capital E and
all), we wrote
[knuthify](https://gitlab.com/islandoftex/libraries/knuthify), a
tiny script that applies Knuth's exact kern values in the browser.

Nine libraries. Each one an idea that started as "this would improve
arara" and ended up as "this improves everything." The bird did not
just get a new version. It got an entire ecosystem.

## The million dollar mistake

Now, let me tell you about a mistake I made more than a decade ago.

When I released arara 1, the idea was beautifully simple: rules
would be written in YAML, and expressions inside those rules would
use MVEL, a scripting language that could talk back and forth to
Java for simple tasks. On paper, this made perfect sense. YAML
would describe what the rule looks like, and MVEL would handle the
logic. Two clean formats, each doing what it does best.

Except that is not what happened. As user demands grew and the
feature set expanded, the complexity of using these two formats
together began to grow. We did some trickery to make them work, and
mixing two syntaxes at the same time was, looking back, not a good
idea at all. The community was patient with us, and we were patient
with the formats, but deep down we knew.

At the same time, something else was happening in the TeX world:
Lua grew up to be a great choice amongst TeX tools. LuaTeX proved
that a real scripting language could live inside a TeX workflow and
feel like it belonged there. So we had the idea of retiring the YAML
plus MVEL combo in favor of pure Lua. Rules as Lua scripts.
Configuration as Lua scripts. One language, one syntax, one thing to
learn.

Here is what that means in practice. This is the heart of the
`clean` rule, one of arara's oldest and most loved companions, in
the old format:

```yaml
commands:
- name: Cleaning feature
  command: >
    @{
        prefix = [];
        if (isUnix()) {
            prefix = [ 'rm', '-f' ];
        }
        ...
```

Look at it carefully. That is a YAML file with a whole other language
hiding inside a string, and the two of them have to agree on
indentation, quoting, and temperament just to delete a few auxiliary
files. Now here is the same rule, the very same bird, in the new
format:

```lua
commands = {
  {
    name = "Cleaning feature",
    command = function(ctx)
      local prefix = {}
      if is_unix() then
        prefix = { "rm", "-f" }
      end
      ...
```

One language, from the first line to the last. No sandwich, no
trickery, no peace treaty between two syntaxes.

It had to be planned. This was not a weekend whim. We knew retiring
two formats that every arara user has been writing rules in for
years would need a transition period. So the YAML engine still
works, it just speaks up once about its retirement, and it will
keep working for a long time. Every official rule ships as twins
during the transition, a `.yaml` and a `.lua` of the same bird, and
a test parses every shipped Lua rule in every gate, so the whole
ruleset is forever proven to work. The helpers speak idiomatic snake
case now, the historic camel case spellings still work, and with
`--engine lua` even the conditionals in your directives become real
Lua expressions: `and`, `or`, and `not` instead of `&&`, `||`, and
`!`, and `{% raw %}{{ ... }}{% endraw %}` tags instead of the old
`@{ ... }` orb tags.

The YAML era enters a graceful retirement. The Lua era begins.

## The whole flock

For most of its life, arara has been a one-file bird. You point it
at a document, it reads the directives, it runs the tasks, and
everyone goes home happy. But that conversation carries a whole
project poorly: a thesis sprawled over directories, a book whose
chapters build in dependency order, a workflow where some files
need their own settings.

Version 7 planted the seed with project specifications. We even
told you, back in March, that we had deprioritized enhancing them.
Consider them enhanced: an arara invocation is now a set of
projects, and the command line is where you name them.

A project specification is a Lua script with a telling extension,
`.proj.lua`, and it returns a small table like this one:

```lua
return {
  name = "The Book Project",
  working_directory = "book",
  files = {
    ["main.tex"] = { },
    ["chapters/chapter1.tex"] = { },
    ["chapters/chapter2.tex"] = {
      priority = 10,
      directives = { "% arara: pdflatex: { draft: yes }" }
    }
  },
  dependencies = { "figures", "extras" }
}
```

Within a project, files run in priority order, ties resolved by
path, so the same specification always runs the same way. Across
projects, dependencies become edges of a graph: pass several
specifications to arara and they merge, the graph decides the
order, every dependency runs before its dependent, and a cycle is
refused outright, with the verdict naming exactly which projects
lie on it. Loose files still ride along as one more project in the
same run. And that is my favorite part of the model: there is no
special case anymore. Point arara at a single loose file, the way
you have always done, and the run is still a set of projects,
exactly one of them: the anonymous project, its files in the order
you typed them, riding the same machinery as any named project.
For arara 8, everything is now a project.

And since every project carries its own working directory, each
one finds its configuration beside its own files, and each one
keeps its own `changed()` memories. The one-file bird learned to
fly with the whole flock.

## Back to the JVM, but the door stays open

In our [maintenance
post](@/news/2026-03-07-arara-maintenance.md), we mentioned that one
of our remaining priorities was making a native executable out of
arara, direction unclear. We explored Kotlin Multiplatform with
genuine excitement. Imagine arara as a native binary, no JVM
required! The dream was compelling.

Then reality arrived. The gap between what Kotlin Multiplatform
promised and what a JVM tool actually needed kept growing. We were
spending more time bridging the gap than building the tool. The
honest call was clear: a JVM tool deserves a JVM build. So we
migrated back to plain Kotlin, and the build got smaller, simpler,
and more honest.

But the door stays open, and I mean that literally. Wherever we
could, we kept building from parts that can travel: arara's file
handling runs on [Okio](https://lysine.dev/okio/), its path model
on a multiplatform path algebra, its command line on
[Clikt](https://github.com/ajalt/clikt), and its data serialization
on [kotlinx-serialization](https://github.com/kotlin/kotlinx.serialization).
Even back on the JVM, the multiplatform door is not just open in
spirit. It is open in the dependency list. If the native dream
ever becomes the dream for today, the tool is already packed for
the trip.

## New plumage

Modern terminal emulators are capable of amazing things: rich
colors, Unicode glyphs, even animation. We looked at arara's plain,
monospace output and thought, the tool deserves better than this.
So we gave it new plumage.

The styled console mode animates every task as it runs, and closes
the run with a verdict line and a summary table naming each file,
its tasks, its time, and its status. A verbose styled run shows the
command it executes, frames the tool's own output as it arrives, and
calls out the conditionally skipped directives instead of letting
them vanish silently. A failed task quotes the tail of its own
output right there in the panel, with the full record kept in the
log. And the recording on our landing page is a real run. No
staging, no editing, just the tool being itself.

We did not stop there. The interactive helpers, the ones that show
messages and ask questions, render as type-tinted dialog boxes in
the styled presentation and as the classic terminal dialogs in the
plain one, both sharing the same reading semantics. A dialog is a
conversation with the person who runs the tool, so both
presentations got the same manners. And when the input is a pipe
and not a person, the dialogs fail loudly instead of guessing. A
tool should never make up an answer to a question nobody heard.

The presentation is honest about its surroundings, too. If your
terminal cannot carry colors or glyphs, the styled mode quietly
degrades to a clean ASCII structure instead of garbling your
screen. Your terminal width is respected. Your eyes are thanked.

## One source of truth

A major release would require a major documentation update, and the
manual got one: all fourteen chapters, rewritten from the first
sentence. To be honest with you, having a single source of truth
for the documentation is not new for us. We have been there before,
when the previous pipeline scraped the rendered website to build
the PDF. What is new is the direction of the generation: this time,
the books are generated from the manual's Markdown sources.

CoralMark converts every chapter into TeX, the diagrams are drawn
through a [Kroki](https://kroki.io/) endpoint into vector figures,
and arara itself
typesets the books, the tool eating its own cooking in the best
possible way. My favorite detail of the whole pipeline is a small
promise of honesty: a figure that has not been rendered yet compiles
as a visible box naming the command that would render it, so the
books always build, never silently missing art.

The same words that become the typeset book also become the pages
you are browsing right now. The [manual](@/manual/_index.md) lives here on the website,
alongside a [quickstart](@/quickstart.md) for the impatient reader
and a [changelog](@/changelog.md) for the historians. One set of words, two presentations, zero drift
between them. The website got the same love, with a new design and
a story to tell.

## The craft

Let me share some of the smaller decisions that shaped this
release, because the small decisions are where the real work lives.

First, a clarification about Java. The jump from version 8 to
version 11 happened in the v7 era, so that was not our doing this
time. For this release, we considered going further, to Java 17,
and we stayed with 11. Reach matters: the oldest runtime we promise
is old enough to be everywhere by now.

How do you prove a promise like that? With a smoke suite that
pulls no punches. One command builds the runnable tool, generates a
matrix of end-to-end scenarios, provisions a scratch world for
them to live in, and runs every scenario twice, once on the JVM we
build with and once on that oldest runtime. The scenarios speak
both engines, test conditionals in both dialects, exercise
sessions, projects, the dry run, the safe mode, and the console in
every mode it offers, and they finish by calling the real pdflatex,
because a TeX automation tool that never typesets anything is a
theory, not a tool. The whole suite also runs green on a real
Windows machine. A promise you test is a promise you keep.

We are proposing arara as a library. The core, the engines, the
everything is now consumable as Maven artifacts, so if you want to
build something on top of arara (a GUI, a CI integration, a very
specific workflow tool), you can. The library defines contracts for
interactive dialogs and ships a headless default, which means your
rules can ask questions without assuming there is a human watching.

We spent a long time finding the right balance when shaping the Lua
rules and Lua configuration files. The helpers had to feel native to
Lua (snake case, as Lua intended) while remaining familiar to arara
users (the historic camel case spellings still work). The
configuration file had to be a real Lua script without feeling like
you need to be a programmer to write one. We went back and forth
on naming, on defaults, on the shape of the API, and we are happy
with where we landed.

And yes, the macOS notarization situation we described in our
[maintenance post](@/news/2026-03-07-arara-maintenance.md) remains
unchanged. The bird still cannot fly into MacTeX, and the reasons
are as honest as they were then. If you happen to be an arara user
with an Apple Developer ID and a generous heart, you know where to
find us.
