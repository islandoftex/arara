arara 8.0.0 is here. This release changes the language rules are
written in, the way the console speaks, and the home the documentation
lives in — while keeping the one thing that made the tool worth
keeping: directives, in your files, doing exactly what you asked.

<!-- more -->

## Rules speak Lua now

The headline of this release: arara rules can be written as **Lua
scripts**, returning a rule table. The helper methods you know from
the YAML format (`getCommand`, `isTrue`, `throwError`, …) are
available as Lua globals, additionally in idiomatic **snake_case**
spellings (`get_command`, `is_true`, `throw_error`, `show_options`,
…) — the form the official rules now ship in. The historic camelCase
spellings keep working throughout the deprecation era.

The new `--engine lua` flag selects the engine, and under it
directive conditionals (`if`, `while`, `until`, `unless`) are
evaluated as **Lua expressions** — compound conditions read `and`,
`or`, `not` instead of `&&`, `||`, `!`. The YAML/MVEL rule format and
the YAML configuration files are deprecated, but they keep working:
no rule breaks on the day you upgrade.

**All official rules have been converted to the Lua format.** The
configuration file speaks Lua as well.

## The console talks back

The new `--console` option selects how arara presents itself, and the
styled mode is a small theatre: every task animates as it runs, every
verdict reports itself, and the run closes with a summary table. The
recording on the landing page is a real run — no staging, just the
tool being itself.

## Several projects, one run

arara now understands **multiple project specifications** in a single
invocation: their projects merge into one dependency graph, a project
that declared no name takes the base name of its specification file,
and loose input files join the run as an anonymous project. Project
specifications are recognized by their suffix alone — a `.proj.lua`
argument is a project, declared and unambiguous, while a plain `.lua`
argument is an ordinary input file. If you are coming from arara 7,
rename your `project.lua` to `project.proj.lua`.

## Dialogs, honestly

Interactive dialogs are now a **host capability**: the library
defines the dialog contract and ships a headless default that raises
a clear error when a rule reaches a dialog, instead of assuming an
interactive terminal. Where a terminal is present, the interactive
helpers — `showMessage`, `showOptions`, `showInput` and `showList`,
in both engines — render as proper terminal dialogs, with wrapped
blocks, a type tag, numbered entries and range prompts, all honoring
the configured terminal width.

## The breaking changes, without the fine print

The changelog carries the complete, honest list. The headlines:
project specifications are recognized by their suffix (rename
`project.lua` to `project.proj.lua`), the Swing dialogs are gone
together with their rules-side plumbing, the message catalog is
redesigned and leaves its old home, the twelve log message constants
are removed from the public API, and the experimental Kotlin DSL
module is no more. The build itself migrated from Kotlin
Multiplatform to plain Kotlin/JVM — a smaller, honest build for a
JVM tool.

## The documentation has a home

You are reading it. The manual was rewritten from the first sentence
to the last, and it lives in two forms that tell the same story: the
PDF book, typeset by the tool itself, and this website — a quickstart
for the impatient, fourteen chapters for the curious, and a changelog
for the historians. The chapters exist once, and both forms read them
there.

## Availability

arara ships in TeX Live and MiKTeX, which makes manual installation
unnecessary for most users — and the [CTAN page](https://ctan.org/pkg/arara)
carries the story for every other case. Enjoy the Lua era! 🦜
